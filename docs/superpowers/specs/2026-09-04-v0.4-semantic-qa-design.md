# v0.4 语义质检设计

## 目标

为 ClaimGuard AI 增加一个可选的、部署在中国大陆的 LLM 语义质检层。现有确定性 QA 与 RAG 证据路径仍可完全离线使用。操作者传入 `--llm` 后，报告会增加经过验证的语义结论，以覆盖短语规则无法可靠判断的客服行为。

## 范围

`v0.4.0` 对每段已完成对话只发起一次结构化模型请求，评估四条语义规则：

| 规则 | 判断内容 |
| --- | --- |
| `SEM-002` | 客服是否回应客户的核心问题？ |
| `SEM-003` | 客服是否敷衍、不耐烦或轻慢？ |
| `SEM-004` | 客户投诉时，客服是否承认并安抚其担忧？ |
| `SEM-005` | 客服是否对结果或时效作出无依据的确定性承诺？ |

本版本不新增 Copilot 回复生成器、Reranking、Citation Judge、Web/API 服务端点、持久化或生产保险数据。

## 选定架构

采用混合工作流。确定性规则和可选 RAG 依据按现有方式执行；`--llm` 随后为完整转录调用一个 `SemanticJudgeClient`。它接收四个允许的语义规则 ID，并返回一组严格 JSON 判定。报告合并器只附加经过验证、且不与既有确定性结论重复的 LLM 违规。

```text
已完成对话
  -> 确定性规则 + 可选 RAG 证据
  -> （仅 --llm）Semantic Judge / qwen3.7-plus / 严格 JSON
  -> 响应验证 + 对话证据验证
  -> 去重后的 QA 报告
```

这优于仅使用 LLM 的报告，因为规则和 RAG 行为仍能离线复现；也优于四次独立 LLM 调用，因为一次结构化请求成本更低，并能让同一对话的语义判断保持一致。

## 模型边界

默认语义模型是通过阿里云 Model Studio 中国大陆 OpenAI-compatible 端点调用的 `qwen3.7-plus`。它支持结构化输出；客户端请求关闭思考模式的严格 JSON Schema 输出。可使用本地 `CLAIMGUARD_SEMANTIC_MODEL` 覆盖模型。复用 `DASHSCOPE_API_KEY` 和 `CLAIMGUARD_DASHSCOPE_BASE_URL` 配置；两者都不得记录或提交。

请求使用适合分类的确定性设置：

- `temperature: 0`
- `enable_thinking: false`
- 带 `additionalProperties: false` 的严格 JSON Schema
- 一段紧凑转录和中文评估指令

阿里云文档说明 `qwen3.7-plus` 支持结构化输出，严格 Schema 输出需要使用受支持的 Qwen 模型。参见官方[结构化输出指南](https://help.aliyun.com/zh/model-studio/qwen-structured-output)和[文本模型列表](https://help.aliyun.com/zh/model-studio/text-generation-model)。

## 裁判契约

响应 Schema 是一个对象：

```json
{
  "findings": [
    {
      "rule_id": "SEM-002",
      "violated": true,
      "evidence": "客服在原对话中说过的完整一句话",
      "reasoning": "中文简要说明",
      "recommendation": "中文改进建议",
      "confidence": "high"
    }
  ]
}
```

每条允许规则最多出现一次。`violated: false` 条目的 `evidence`、`reasoning` 和 `recommendation` 为空字符串；`confidence` 只能为 `high`、`medium` 或 `low`。

客户端验证 JSON 类型、允许的规则 ID、重复 ID 和精确字段约束。集成层还验证每个 `violated: true` 的证据字符串精确等于输入对话中一整条非空客服消息。无效服务商响应会抛出简洁的 `SemanticJudgeError`，且不生成部分报告。

## 报告契约

`Finding` 新增可选字段：

- `reasoning`：验证后的 LLM 说明，否则为 `null`。
- `confidence`：验证后的 LLM 置信度，否则为 `null`。
- `judge`：v0.4 LLM 结论为 `semantic_llm`，否则为 `null`。

既有报告字段和双参数 `generate_qa_report` 的旧用法保持不变。重复规则 ID 时，确定性结论优先，以保持普通离线 fixture 结果稳定。LLM 结论使用既有规则目录提供名称、类别和风险等级。

## CLI 与失败行为

只在现有对话 QA 路径增加 `--llm`，它不能与 `index` 命令一起使用。未传入 `--llm` 时，不创建语义模型客户端，也不发起网络请求；传入后，CLI 会在加载对话后惰性创建客户端。

缺少凭据、网络错误、非 200 响应、格式错误 JSON、Schema 违规或无效引用证据时，命令以代码 `2` 退出，在 stderr 输出简洁信息，且绝不包含 API Key 或 Authorization header。

## 测试与评估

所有自动化测试使用注入的传输器和字面模型响应；没有测试调用远程 API。覆盖范围包括：

- 精确的 OpenAI-compatible 请求形状和无凭据泄露；
- 有效严格 JSON 解析；
- 格式错误 JSON、不受支持 ID、重复 ID、无效置信度和编造证据拒绝；
- 确定性/LLM 结论去重与补充报告字段；
- 旧版 CLI、`--index` 和 `--llm` 命令路径；
- 回答不相关、不耐烦、未安抚投诉和无依据承诺的中文 fixture。

一次手动发布检查可以使用被忽略的本地 `.env` 运行 `claimguard <fixture> --llm`。需检查输出中的有依据、带完整引文的结论；Key 和生成的本地文件保持在 Git 之外。
