# v0.4 Semantic QA Design

## Goal

Add an opt-in, China-local LLM semantic quality-inspection layer to ClaimGuard
AI. The existing deterministic QA and RAG evidence paths remain available and
fully offline. When an operator requests `--llm`, the report gains validated
semantic findings for customer-service behavior that phrase rules cannot cover
reliably.

## Scope

`v0.4.0` evaluates four semantic rules in one structured model request per
completed conversation:

| Rule | Decision |
| --- | --- |
| `SEM-002` | Does the agent address the customer's central question? |
| `SEM-003` | Is the agent dismissive, impatient, or perfunctory? |
| `SEM-004` | When the customer complains, does the agent acknowledge and soothe the concern? |
| `SEM-005` | Does the agent make an unsupported definite promise about an outcome or timing? |

The release does not add a Copilot reply writer, reranking, a citation judge,
web/API server endpoints, persistence, or any production insurance data.

## Chosen Architecture

Use a hybrid workflow. Deterministic rules and optional RAG grounding run as
they do today. The `--llm` flag then invokes one `SemanticJudgeClient` for the
completed transcript. It receives the four allowed semantic rule IDs and
returns one strict JSON decision set. A report merger appends only validated
LLM violations that do not duplicate an existing deterministic finding.

```text
completed conversation
  -> deterministic rules + optional RAG evidence
  -> (--llm only) Semantic Judge / qwen3.7-plus / strict JSON
  -> response validation + transcript-evidence validation
  -> deduplicated QA report
```

This is preferable to an LLM-only report because the rule and RAG behavior
remain reproducible offline. It is preferable to four independent LLM calls
because one structured request lowers cost and keeps semantic decisions
coherent for one conversation.

## Model Boundary

The default semantic model is `qwen3.7-plus` through Alibaba Cloud Model
Studio's mainland OpenAI-compatible endpoint. It supports structured output;
the client requests strict JSON Schema output with thinking disabled. The
model can be overridden locally with `CLAIMGUARD_SEMANTIC_MODEL`. The existing
`DASHSCOPE_API_KEY` and `CLAIMGUARD_DASHSCOPE_BASE_URL` configuration are
reused; neither value is logged or committed.

The request uses deterministic settings appropriate for classification:

- `temperature: 0`
- `enable_thinking: false`
- strict JSON Schema with `additionalProperties: false`
- one compact transcript and a Chinese evaluation instruction

Alibaba Cloud documents that `qwen3.7-plus` supports structured output and
that strict schema output requires supported Qwen models. See the official
[structured output guide](https://help.aliyun.com/zh/model-studio/qwen-structured-output)
and [text model list](https://help.aliyun.com/zh/model-studio/text-generation-model).

## Judge Contract

The response schema is a single object:

```json
{
  "findings": [
    {
      "rule_id": "SEM-002",
      "violated": true,
      "evidence": "客服在原对话中说过的完整一句话",
      "reasoning": "中文简要说明",
      "recommendation": "中文改进建议",
      "confidence": "high"
    }
  ]
}
```

Each allowed rule appears at most once. `violated: false` entries carry empty
strings for evidence, reasoning, and recommendation. Confidence is one of
`high`, `medium`, or `low`.

The client validates JSON types, allowed rule IDs, duplicate IDs, and exact
field constraints. The integration also validates that every `violated: true`
evidence string is a non-empty substring of an agent message in the input
conversation. Invalid provider responses raise a concise `SemanticJudgeError`
and produce no partial report.

## Report Contract

`Finding` receives additive optional fields:

- `reasoning`: the validated LLM explanation, otherwise `null`.
- `confidence`: the validated LLM confidence, otherwise `null`.
- `judge`: `semantic_llm` for v0.4 LLM findings, otherwise `null`.

Existing report fields and legacy two-argument `generate_qa_report` behavior
remain unchanged. Deterministic findings win on duplicate rule IDs so ordinary
offline fixture results remain stable. LLM findings use the existing rule
catalog for names, category, and risk level.

## CLI and Failure Behavior

Add `--llm` to the existing conversation QA path only. It is invalid with the
`index` command. Without `--llm`, no semantic model client is created and no
network request occurs. With `--llm`, the CLI creates the client lazily after
the conversation has loaded.

Missing credentials, network errors, non-200 responses, malformed JSON, schema
violations, or invalid quoted evidence exit with code `2`, emit a concise
message to stderr, and never include the API key or Authorization header.

## Testing and Evaluation

All automated tests use injected transports and literal model responses; no
test calls the remote API. Test coverage includes:

- exact OpenAI-compatible request shape and no credential disclosure;
- valid strict JSON parsing;
- malformed JSON, unsupported IDs, duplicate IDs, invalid confidence, and
  fabricated evidence rejection;
- deterministic/LLM finding deduplication and additive report fields;
- legacy CLI, `--index`, and `--llm` command paths;
- Chinese fixtures for relevance failure, impatience, unresolved complaint,
  and unsupported promise.

One manual release check may run `claimguard <fixture> --llm` using the ignored
local `.env`. Its output is reviewed for grounded, quote-backed findings; the
key and generated local files remain outside Git.
